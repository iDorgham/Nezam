# Wireframes — Contract & Operations

> Canonical reference for `wireframes_locked.json` schema, the architecture ↔ wireframe binding (`arch_page_id`), and the `/develop` hardlock behavior. Read alongside DESIGN.md §7 (Wireframe Rendering Contract).

## 1. Lock export path

The single source of truth for committed wireframe state is the root file:

```
wireframes_locked.json   (committed)
.nezam/design-hub/wireframes_locked.json → ../../wireframes_locked.json (symlink)
```

Two readers, one byte stream. Editing either path edits the same file.

### Export trigger

1. Open Design Hub at `localhost:4000`
2. Architecture → build page tree
3. Wireframes → compose blocks per page
4. Approve every page (`layout_approved: true`)
5. Click **Export Lock** → writes `wireframes_locked.json` at repo root

### Schema (top-level keys)

| Key | Type | Purpose |
|---|---|---|
| `meta` | object | project_name, project_slug, locked_at, profile, nezam_version |
| `locked_at` | ISO-8601 | Top-level mirror of `meta.locked_at` |
| `design_decisions` | object | layout_direction, color_mode, motion_level |
| `sitemap.pages[]` | array | Architecture-derived ordered page list (lock view) |
| `pages[]` | array | Per-page block layouts (renderer view) |
| `design_system` | object | color_profile, typography, spacing, borders |

Full structural validation lives in `.nezam/core/scripts/checks/check-wireframes-lock.js` — run via `node` or in CI (`wireframe-validation.yml`).

## 2. `arch_page_id` mapping (1:1 binding contract)

The architecture model (in-app, mutable) and the lock model (committed, immutable per release) speak two id namespaces. The `arch_page_id` field is the bridge.

### Two id spaces

| Space | Owner | Example |
|---|---|---|
| Architecture id | Designer (Architecture tab) | `home`, `pricing`, `dashboard.settings` |
| Lock id | Deterministic generator (`toLockPageId(idx)`) | `PAGE-001`, `PAGE-002`, … |

### Binding rule

In `wireframes_locked.json#sitemap.pages[]`, every entry **must** carry both:

```jsonc
{
  "id": "PAGE-001",          // lock id (deterministic, by order)
  "arch_page_id": "home",    // architecture id (designer-named)
  "title": "Home",
  "route": "/",
  // …
}
```

Source: `.nezam/design-hub/src/lib/locking/build-lock-payload.ts` — `buildLockPayload()` produces this binding by mapping `ArchPage[]` → `LockSitemapPage[]` in deterministic order.

### Resolution priority (reader side)

`WireframesSection.tsx` and `lock-session-resolver.ts` resolve a page by:

1. **Prefer `arch_page_id`** — designer-stable, survives lock id renumbering
2. **Fallback to legacy `id`** (`PAGE-001` form) — for pre-binding lock files

Test coverage: `.nezam/design-hub/src/test/lock-session-resolution.test.ts` (asserts both paths) and `build-lock-payload.test.ts` (asserts deterministic ordering).

### Why the 1:1 rule

| Without binding | With `arch_page_id` |
|---|---|
| Renaming a page in Architecture orphans its wireframe sessions | Sessions follow the page across renames |
| Re-exporting the lock invalidates downstream references | `arch_page_id` is stable across re-exports |
| No way to diff "same page, new layout" | Diff by `arch_page_id`, ignore renumbered `id` |

### Mapping table (current lock)

> Generated by hand for this release; future tooling will emit this section from `wireframes_locked.json` on lock export.

| Lock id (`id`) | Architecture id (`arch_page_id`) | Title | Route |
|---|---|---|---|
| PAGE-001 | home | Home | `/` |
| PAGE-002 | dashboard | Dashboard | `/dashboard` |
| PAGE-003 | wireframe | Wireframes | `/wireframe` |
| PAGE-004 | design | Design | `/design` |
| PAGE-005 | export | Export | `/export` |
| PAGE-006 | signin | Sign In | `/sign-in` |

When the next lock export runs through `buildLockPayload`, each entry will carry both ids per the binding rule above.

## 3. Hardlock behavior — what `/develop` refuses

The lock file participates in the SDD hardlock for Build P1+. Refusal conditions:

| Condition | `/develop` response |
|---|---|
| `wireframes_locked.json` missing from repo root | 🔒 HARDLOCK VIOLATION — "wireframes_locked.json missing" |
| File present but JSON invalid | 🔒 same |
| `meta.locked_at` missing or not ISO-8601 | 🔒 same |
| `meta.project_name` / `profile` / `nezam_version` missing | 🔒 same |
| Any `sitemap.pages[].id` missing required field (`id`, `title`, `route`, `status`) | 🔒 same |
| `sitemap.pages[].arch_page_id` not in `pages[].page_id` set | ⚠️ warning, not blocking (legacy locks tolerated) |

These rules are enforced by:

- **CI:** [`.github/workflows/wireframe-validation.yml`](../.github/workflows/wireframe-validation.yml) (job `lock-schema`)
- **Local:** `node .nezam/core/scripts/checks/check-wireframes-lock.js`
- **Pre-commit:** `pnpm ai:check` does NOT include the lock validator today — add to `.husky/pre-commit` if you want belt-and-braces

### Manual verification recipe

```bash
# Confirm the lock exists and validates
node .nezam/core/scripts/checks/check-wireframes-lock.js
# Confirm the readiness gate still passes
bash .nezam/core/scripts/checks/check-onboarding-readiness.sh
# Confirm /develop start would not be blocked by a missing lock
ls -la wireframes_locked.json .nezam/design-hub/wireframes_locked.json
```
